## V82 · 桌面右键两条（用户 09-28 00:26 反馈）

用户原话：

1. 「现在**新建文件夹还是卡住的**哇」
2. 「@image 你看图片 不是说不能影响默认图标右键菜单行为，这么玩意 **我的电脑都变成这样了**」

### 取证

- 应用日志（`%LOCALAPPDATA%\Handy\handy.log`）：V81 装完后只有两条「系统菜单旁听已启动」
  （00:05:54 / 00:06:48），**一条借出记录都没有** ⇒ 借出机制静默失效。
- 截图里的菜单 = 前端 `menuLoose`（标题 + 打开 + 打开文件位置 + 「拖进任意格子即可收纳」）。
  代码里 `entry.isSystem` 被无条件排除在原生菜单之外，注释写着「系统图标没有文件路径，
  Shell 给不了菜单」—— **这句话是错的**。
- 新写的 `scripts/audit/menu_dump` 实测（`cargo run --release --example menu_dump --
  "::{20D04FE0-3AEA-1069-A2D8-08002B30309D}"`）：此电脑的 CLSID **拿到 14 项**完整原生菜单
  （打开 / 固定到快速访问 / 搜索 Everything / 管理 / 映射网络驱动器 / 创建快捷方式 /
  删除 / 重命名 / 属性…）。命名空间对象完全能走 `SHCreateItemFromParsingName`。
- `scripts/audit/desktop-icon-probe.py`：`SysListView32` 确实已被 `SW_HIDE`，`DefView` 仍可见。

### 根因

**借出判据失效**。`EVENT_SYSTEM_MENUPOPUPSTART` 的 `hwnd` 实测给的是**菜单窗 `#32768` 自己**
（不是「菜单所属的窗口」），而 V81 的判据只认「就是桌面视图 / 它的父」和「顶层是
`Progman` / `WorkerW`」—— `#32768` 的顶层就是它自己、类名也叫 `#32768`，**两条双双落空**，
于是每一次桌面右键都在 `is_desktop_menu` 里被静默判掉。

### 修法

1. **前端**（`GridOverlay.tsx`）：系统入口（此电脑 / 回收站 / 用户的文件）的右键也走
   `ipc.shellContextMenu(entry.path)`；只有原生菜单拿不到时才回落到我们自己的菜单
   （降级成兜底）。
2. **`is_desktop_menu` 判据重排**（`platform/desktop_handoff.rs`），任一条成立即认：
   ① `hwnd`（或 `#32768` 的 **owner**）就是桌面视图 / `DefView`；
   ② 同上的顶层是 `Progman` / `WorkerW`；
   ③ **看菜单压在谁身上**（菜单左上角外侧 1px 的 `WindowFromPoint`）—— 这条不依赖前台是谁，
      用户刚点过浏览器再回来右键桌面时只有它还能认出来；压在别的应用窗口上则直接否掉；
   ④ 同进程 + 顶层在桌面链上；⑤ 前台是桌面背景；⑥ 是 Shell 的菜单窗且前台不是别的应用。
3. **`poll_menu()` 轮询兜底**：`commands::grid` 的保险轮询每 25ms 直接问一次
   「`#32768` 在不在」，不再把整套机制赌在一个语义含糊的事件参数上。两条路并存
   （`begin_handoff` 幂等）。
4. **`TAKEBACK_PENDING` 去重**：轮询路线会反复问「菜单还在吗」，没有闸门就会每 25ms
   spawn 一个收回线程。

### 新增诊断脚本（`scripts/audit/`）

- `desktop-menu-probe.py`：装 WinEventHook 观察菜单事件参数（含类名 / pid / owner / root）。
- `desktop-hit-probe.py`：把光标挪到采样点再问 `WindowFromPoint` —— 判「空白处的鼠标
  落到谁身上」（穿透是否有效）。
- `desktop-menu-roundtrip.py`：找穿透点 → 真模拟一次右键 → 看日志有没有借出 → Esc 收菜单。

> 顺带查到的环境情况：探针跑到「桌面被一个**最大化的 Chrome 窗口**
> （`Chrome_WidgetWin_1` / pid 2972 / 标题 `ops-ai-agent-platform-design`）盖住」，
> 15 个采样点里 14 个落在它身上。做这类桌面取证前要先确认桌面没被别的窗口压着。

## V83 · 双显示器几何（用户 09-28 01:00 反馈）

用户原话：

> 「@image 我有双显示器后变成了这样，如果是双显示器你看怎么做了，是根据每个显示器自己的
> 分辨率做还是只计算主显示器，你自己决定」

### 取证（决定性）

`scripts/audit/display-probe.py`（本轮新写）实测：

```
主显示器工作区（几何真源）：位置 (0,0) 尺寸 1920×1032
挂件窗 pid=30036 visible=True  实际：位置 (0,0) 尺寸 1138×608
偏差：dx=+0 dy=+0 dw=-782 dh=-424   ❌ 未对齐
```

而 `grid_meta.overlay_geometry` = `{"x":0,"y":0,"width":1138,"height":608}` —— **一字不差**。

### 根因

几何被**持久化**、且开窗「DB 优先」：

1. 前端挂载时读**一次** `scaleFactor`，之后窗口 `moved` / `resized` 停稳 500ms 就
   `gridGeometrySet` 写库（`GridOverlay.tsx` 里那段 useEffect）；
2. 接上第二块屏时系统会移动甚至改掉我们的窗口尺寸（DPI 变了要重排）⇒ 触发 `resized`；
3. 那次换算用的是**过期的 `scaleFactor`** ⇒ 存进库的是错值；
4. 从此开窗一律按这个错值 ⇒ **永久锁死**（窗口 `resizable(false)` + `decorations(false)`，
   用户根本没有调整它的途径）。

截图里内容挤在左侧约 1138 宽、右边 782px 全空 —— 与实测完全一致。

### 决策：**只算主显示器**（用户授权「你自己决定」）

已写进 `docs/02-architecture/DESKTOP-LAYER.md` §1.2。三条理由：

1. 系统做不到「主屏接管 + 副屏保留原生图标」：`SysListView32` 是**横跨整个虚拟桌面的
   单一视图**，只能整体显示/隐藏；
2. 便签 / 工作台 / 竖条是**单实例**语义，双屏各铺会产生「同一份内容在哪块屏」的歧义；
3. 双屏各铺需要每屏一个窗口（WebView2 跨不同缩放的屏会渲染模糊、尺寸跳变），是独立特性。

副产品：**副屏完全原生**（那里没有我们的窗口，右键/新建/拖拽都不经过 Handy）。

### 改动

- `commands/grid.rs`：新增 `primary_work_area()`（物理像素真源）、`sync_overlay_bounds()`
  （幂等对齐，带 **2px 容差** + 连续 5 次失败退避 5 分钟）、`bounds_need_fix()`（纯函数，带单测）、
  `drop_legacy_geometry()`（清脏键）；`ensure_overlay_window` 复用分支加对齐（`show` 前）、
  新建分支 build 后 `show` 前对齐；保险循环每 40 拍（1s）复核并广播 `grid:bounds-changed`；
  `layout_work_size` 改成**主屏优先**；**删掉** `GridGeometry` / `read_geometry` /
  `grid_geometry_get` / `grid_geometry_set`（`lib.rs` 同步去掉注册）。
- 前端：删掉几何持久化那段 useEffect 与 `GEOMETRY_SAVE_DEBOUNCE_MS`；新增
  `grid:bounds-changed` → `relayoutSoon()`；`ipc.ts` / `types/grid.ts` 删 `GridGeometry` 相关。
- 新脚本 `scripts/audit/display-probe.py`：显示器配置 vs 挂件窗几何对照（双屏排查用）。

# 2026-10-08 · 架构诊断（本轮无代码改动，只出结论 + 路线）

## 用户质疑（原话）
> 改了这么多版本，桌面整理还是跟原生桌面不一样，没法做到跟腾讯桌面整理一样的效果吗？腾讯把原生桌面图标/文件整理到格子里，图标/目录/文件的原生右键、属性全部没变。我们貌似就是一个完全独立的桌面网页页面？而且新建文件夹/新建文本文档等右键功能都不是原生的，问题很多。

## 诊断：三条事实（都已取证，不是推测）
1. **腾讯也是自绘覆盖层，不是「保留原生图标」**。博客园那篇用 Spy++ 实测：「腾讯桌面整理的窗口，实际上就是自己做了一个窗口，覆盖在桌面列表窗口上面，让其 Z 序高于桌面列表窗口即可，然后再在桌面整理窗口上显示出所有桌面文件并将当前桌面主题背景绘制在这个窗口上」。另一篇：「系统自带的桌面图标列表常常被接管或隐藏」。**百度百科还记着它修过「Win11 风格右键菜单新建文件无法直接重命名的 Bug」——和我们踩的是同一个坑。**
   ⇒ 「自绘」不是问题，**「能力从哪来」才是问题**。
2. **我们的条目能力其实已经是原生的**：`platform/shell_menu.rs` 走 `BindToHandler(BHID_SFUIObject)` → `IContextMenu::QueryContextMenu` → `TrackPopupMenuEx(TPM_RETURNCMD)`，且转发 `IContextMenu2/3` 消息（懒加载子菜单）。图标走 `SHParseDisplayName` + `SHGetFileInfoW`。**这半边和腾讯同构。**
3. **三处硬伤是我们自实现出来的**（不是自绘造成的）：
   - **桌面/格子空白右键**：靠 V81/V82/V84 的「借出桌面」绕过（V86 又加「编辑框借出」补丁）。本质是补丁，不是解法 ⇒ 用户感觉「新建不是原生的」。
   - **拖拽**：V59 起是**指针拖拽**（自算落点、自画幽灵），**不进系统拖放循环**。根因是 wry 的 `IDropTarget` 对无 `CF_HDROP` 载荷不写 `*pdwEffect`。后果：拖不到微信/PS/浏览器、没有原生拖拽光标。
   - **格子内空白右键**：只有 Handy 自己的菜单，**没有「新建」**（腾讯格子内可以直接新建）。
   - 缺项：单击两次 / F2 重命名、排序方式 / 查看方式。

## 建议路线（待用户拍板，不要擅自开工）
- **第一步（核心）**：空白右键不再借出，改为自己弹**桌面文件夹的原生背景菜单**（`SHGetKnownFolderItem(FOLDERID_Desktop)` → `IShellItem` → `IContextMenu` → `QueryContextMenu` → `TrackPopupMenuEx`），新建后让**我们列表里的对应条目**进入自绘 inline 改名。顺手把同一菜单挂到**格子内空白**。
  ⇒ 副产品：V81/V82/V84 那套「借出 / 收回竞速 / `#32768` 判定 / 安静 1.5s」可以**整体删除**。
  ⚠️ 待验证（不要赌）：`FOLDERID_Desktop` 拿到的背景菜单是否含「新建/粘贴/刷新/个性化」全套。**先做验证再动工。**
- **第二步**：拖拽升级为真 OLE 拖源（`IDataObject` + `CF_HDROP` + `DoDragDrop`）。风险中等：`DoDragDrop` 是模态循环，且**我们自己的窗口也是 drop target**（Tauri `dragDropEnabled`）⇒ 必须拒绝自身 drop，否则自吞。
- **第三步**：补 F2/单击两次重命名、排序方式、查看方式。

## 探针实测结果（已证实，不是推测）
`src-tauri/examples/bg_menu_dump.rs`（新建）。三条路线对比：

| 路线 | 做法 | 结果 |
|---|---|---|
| A0（作废） | `SHGetKnownFolderIDList(FOLDERID_Desktop)` → `root.BindToObject` | ❌ `E_INVALIDARG 0x80070057` —— **FOLDERID_Desktop 的 PIDL 就是命名空间根本身**，Root 没有父可绑 |
| **A1（采用）** | **`SHGetDesktopFolder()` → `CreateViewObject(IID_IContextMenu)`** | ✅ **16 项，含「新建(&W)」+「下一个桌面背景」+「显示设置」+「个性化」+ 我们注入的「Handy 桌面整理」+ 全部第三方扩展** |

## V88 已落地（用户报障：新建报错 + 卡 + 整体刷新 + 改名不刷新）

### 问题根因（已取证）
- **新建报 E_FAIL (0x80004005)**：V87 的 `CreateViewObject(None)` 背景菜单是**没有真实 view 的 view-object 菜单**，其「新建」是 Shell 的 `CNewMenu`，要靠 `IShellView` 才能定位目标目录并进改名框；我们直接 `InvokeCommand` 这条「新建」动词 ⇒ E_FAIL。日志 `21:00:34 桌面背景菜单失败：执行菜单命令失败：未指定的错误 (0x80004005)` 正是此。
- **改名后仍是老名字**：前端只调异步 `refresh()`，内部 `Promise.all` 任一 `gridItemList` 抛错则整批 `items` 不更新，且 `catch(()=>undefined)` 吞错。后端磁盘+DB 都成功（脚本核验过磁盘确有 `123123` 等新名、DB 无失效行）。

### 修法
1. **改名 UI 不刷新（已修）**：`commitItemRename` 内改为**先本地同步改 `items`/`loose`/`selectedPaths`**，再 `refresh()` 对齐布局。
2. **新建报错 + 卡 + 整体刷新（本批核心）**：不再赌 IShellView（脆弱、跨版本不稳），改为在 `run_menu` 里**自己注入「新建」子菜单**（文件夹/文本文档，命令 id 0x9001/0x9002，避开 Shell 的 1..=0x7FFF），点中后在桌面用户目录按 Windows 命名规则（`新建文件夹`→`新建文件夹 (2)`…）建**真实**目录/文件，再 `app.emit("grid:item-created", {path,name})`。
3. **消除卡/整体刷新**：前端 `openDesktopBackgroundMenu` 注册一次性 `grid:item-created` 监听；命中则**只 `fetchLoose(false)` + 进原地改名**，**不**触发全量 `refresh()`；其它菜单项才走原全量对账。菜单收起后给 30ms 窗口等事件，没等到再走全量。

## V90 —— 不复刻了：把右键**转发**给 Explorer 的桌面视图

用户 23:01 发两张对比图质问「这是你搞得右键菜单，你到底能不能能实现原始功能」：

- **图1（退出接管后右键）** = Explorer 原生菜单：查看 / 排序方式 / 刷新 / 下一个桌面背景 /
  撤销 删除 / **新建（14 项：文件夹、快捷方式、BMP 图像、DOC、DOCX、WPS PDF、PPT、PPTX、
  WPS AI 生成 PPT、RTF、文本文档、XLS、XLSX、360压缩 ZIP）** / 显示设置 / 个性化 /
  在终端预览中打开 / 显示更多选项；
- **图2（接管态右键）** = 我们复刻的菜单：**只有「新建文件夹 / 新建文本文档」两项**，
  连「查看 / 排序方式 / 刷新」都没有。

日志对齐了这两张图：`23:01:07 交还系统桌面图标 + 收起挂件层`（退出接管 → 原生菜单）、
`23:01:21 接管桌面图标`（重新接管 → 我们的菜单）。

### 技术裁决（写进 `shell_menu.rs` 文档）
那两块**根本不经过 `IContextMenu`**，不是「没做」，是接口边界：
- 查看 / 排序 / 刷新 → `IShellView::GetItemObject(SVGIO_VIEWMENU)`
- 完整新建列表 → `CNewMenu` + 注册表 `ShellNew`（还要真实 `IShellView` 才能定位目录 + 改名）

我们手上只有 `IShellFolder::CreateViewObject(IID_IContextMenu)` 那张**残缺**菜单。**复刻永远追不平** ⇒ 改转发。

### 实现
`SHELLDLL_DefView` / `SysListView32` 并没消失，接管只是 `SW_HIDE`。给它发
`SendMessageW(list, WM_CONTEXTMENU, wParam=list, lParam=MAKELPARAM(screen_x, screen_y))`
→ 它按 shell 约定转给父窗口 DefView → DefView 取 `SVGIO_BACKGROUND` 弹**完整原生菜单**；
而 listview **始终隐藏** ⇒ 桌面**不翻白**。

- `SendMessage` 跨进程同步：菜单是模态循环，**真弹出来了就一定阻塞**。判据 `ms >= 150`；
  没弹 → `Ok(false)` → **回退 V89 复刻菜单**（最坏不比以前差）。
- 弹之前先 `SetForegroundWindow(我们的可见挂件窗)`：菜单宿主是**隐藏的** DefView，
  不先占前台菜单会「点外面不消失」。
- **收尾必做**：原生「新建」会让 Explorer 在**隐藏的** listview 上拉起**原位改名框** ——
  ①用户看不见（=「新建完没反应」）②**抢键盘**（我们自己的改名输入框就打不进字）。
  所以 `sleep(60ms)`（CNewMenu 拉起改名框有一段异步）后发
  `LVM_CANCELEDITLABEL`(0x1077) + `WM_CANCELMODE`，把「认领 + 改名」交回前端。
- 前端：原生路径回 `null` ⇒ **增量对账**（`before`/`after` diff）；**只有出现删除才 `refresh()`**
  （单纯新建只进竖条 + 原地改名，不整层重排）。

  每次右键都是这个形态 ⇒ **V90 的判据把「弹出」全判成了「没弹出」**。
- `cargo run --release --example bg_menu_dump`（落盘 `.build-logs/bg_menu_dump.txt`）：
  `CreateViewObject` 的桌面背景菜单 = **16 项**，内容是「第三方扩展…/搜索 Everything/
  Handy 桌面整理/下一个桌面背景/新建/显示设置/个性化」——**没有查看 / 排序方式 / 刷新 /
  在终端预览中打开 / 显示更多选项**。
- 用户图1 的菜单**有**那五项 ⇒ 那张菜单**不是我们弹的**，是 **Explorer 自己弹的**。
  ⇒ 结论：**转发其实是成功的**，只是**异步**（Win11 的菜单由 XAML 宿主在**别的线程**弹出，
  `SendMessage` 打完招呼就回来）。V90 拿「耗时 ≥ 150ms」当判据 ⇒ 必然误判。
- 于是每次右键 = 「Explorer 的原生菜单」+「我们的回退复刻菜单」**同屏两个**；
  且 Explorer 那个因为我们的 `TrackPopupMenuEx` 抢了模态前台**收不回去** ⇒ 「一直存在」。

### 修法（V91）
1. **删掉耗时判据**，改成**直接观测屏幕**：`WindowFromPoint(光标)` + `GetAncestor(GA_ROOT)`
   取鼠标点下的顶层窗口；转发后轮询 ≤1000ms，一旦「换了人 **且** 不是本进程」⇒ 菜单真弹了。
2. **转发后必须等菜单收起**才返回（`≤60s`）：否则命令立刻 resolve ⇒ 前端在**菜单还开着**时
   对账 ⇒ diff 永远是空 ⇒ 用户点「新建」建出来的文件**永远进不了竖条**（V90 的隐藏 bug）。
3. **等待不许占 UI 线程**（纯 sleep 循环没有消息泵 ⇒ 整个前端冻住）⇒ 拆成两半：
   `forward_desktop_view_menu()`（UI 线程，只发消息，立即返回现场）+
   `await_desktop_view_menu()`（**后台线程**轮询等出现/等收起）；转发不生效时才
   `run_on_main_thread` 回 UI 线程弹 V89 复刻菜单（`TrackPopupMenuEx` 要消息泵）。
4. 取消隐藏改名框改走 **`PostMessageW`**（投递即走，不会被忙线程卡死），并在
   **「等菜单收起」的循环里持续打点**（改名框是菜单收起那一刻才拉起的，V90 单次 60ms 碰不上）。

## V58 · 修「整理把桌面图标原始的右键行为改变了」（用户 1 条反馈 + 1 截图）

> 用户原话：「为什么我们的整理把桌面图标原始的右键行为改变了，例如这种文件 文件夹右键
> 应该有 rar 压缩工具的，2.还有其他的我们不能改变桌面默认行为，我们只是整理位置，
> 为什么你把桌面图标的行为等全都改变了呢」

### 结论

**3 条我们自己造成的真缺陷（全部已修）+ 1 条拿不到的项（360压缩，对方策略，非代码可修）。**

### 调查：新建诊断工具 `src-tauri/examples/menu_dump.rs`

`IContextMenu::QueryContextMenu` 只填充不弹出 ⇒ 可无人值守枚举任意路径的菜单项**与子菜单内容**。
本次所有结论都由它 + 两把「二分刀」得出：

1. 同一路径换 `flags` → 分清「Shell 不给」还是「我们没要」；
2. 把同一个 exe 复制改名成 `explorer.exe` 再跑 → 分清「大家都拿不到」还是「只有我们拿不到」。

### 缺陷 ① `QueryContextMenu` 的 `uFlags` 一直传 0

`flags=0` → 菜单里**没有「重命名」**；`flags=0x14`（`EXPLORE|CANRENAME`）→ `[19] 重命名(&M)` 出现。
用户截图里缺的正是它。现按 Explorer 口径传 `CMF_NORMAL | CMF_EXPLORE`。
**刻意不传 `CMF_CANRENAME`**：「重命名」是 `DefView` 视图实现的原位改名，不是菜单命令；
我们不是它的视图，传了只会得到点了没反应的死项（详见 CONVENTIONS §31.4）。

### 缺陷 ② 从不转发 `WM_INITMENUPOPUP`（影响面最大）

Shell 与第三方扩展的子菜单**懒加载**，真内容在 `WM_INITMENUPOPUP` 里补。修前实测：

```text
发送到(&N)      └ 子菜单只有 1 项：蓝牙设备
包含到库中(&I)  └ 子菜单只有 1 项：正在检索库...   ← 占位文案直接露给用户
```

修法：菜单期间**窗口子类化**，把四条菜单消息转给 `IContextMenu2/3::HandleMenuMsg(2)`，
其余原样 `CallWindowProcW` 交回（只旁听，不改宿主行为），菜单收起即还原。
两条坑：先 clone 接口再**释放 `RefCell` 借用**（否则重入 panic）；`WM_MENUCHAR` 要**自己 return**。

### 缺陷 ③ Shift + 右键被我们抢了

Shift + 右键在 Explorer 里是**扩展菜单**（在此处打开 PowerShell 窗口…），属系统语义。
现在 Shift → 透传 `CMF_EXTENDEDVERBS`；Handy 自己的条目菜单改挂 **Ctrl + 右键**（原生无含义），
提示文案同步改成 `Ctrl+右键更多操作`。

### 拿不到的项：360压缩

本机压缩软件是 **360压缩**（`C:\Program Files (x86)\360\360zip\360ZipExt64.dll`，
`Directory\shellex` + `*\shellex`，x64、CLSID 正常、未被 Blocked）。但它**只认进程名
`explorer.exe` 的宿主**：同一份工具、同一条 `dify.zip`，`menu_dump.exe` 得 40 项且**没有**
360压缩；改名成 `explorer.exe` 后 **45 项**，360压缩四项全出现。DLL 里同时有宽字符串
`explorer.exe` / `360ExtLoader.exe` 并导入 `CreateProcess` —— 按宿主进程名分流。
**换任何工具都一样**，我们没有可修之处。

### 顺带核实

- `platform/desktop_menu.rs` 只往 `HKCU\...\DesktopBackground\Shell` **加**一条 Handy 入口，
  是**增项**，没删改系统的项；桌面空白处右键仍是 V53 的原生菜单。

## V59 · 修「图标拖不动（拖动显示禁用符号）」+「高度方向重叠 / 装不下不出滚动条」（用户 3 条反馈 + 2 截图）

> 用户原话（07:47）：「看图片为什么自动整理 你看图片中红圈的位置高度方向还是有点重叠呢
> 2.图标还是不能自己拖动，拖动就显示禁用图标
> 3.我列表展开格子装不下了应该自动出滚动条哇」

### 结论

**3 条反馈、2 个根因，都在「我们看不见的那一层」。**

### 根因 ①（第 2 条）HTML5 拖放在挂件窗里**被 wry 判死**

本机读 `~/.cargo/registry/src/*/wry-0.55.1/src/webview2/drag_drop.rs`：

```rust
fn DragEnter(pDataObj, ..., pdwEffect) {
    let hdrop = iterate_filenames(pDataObj, ...);   // 只认 CF_HDROP（真实文件）
    if !enter_is_valid { return Ok(()); }           // 直接返回 —— **一个字都不写 *pdwEffect**
}
fn DragOver(..., pdwEffect) { *pdwEffect = *self.cursor_effect.get(); }  // 初值 DROPEFFECT_NONE
```

图标是 DOM 元素 ⇒ 载荷没有 `CF_HDROP` ⇒ `DragOver` 每个像素回填 `DROPEFFECT_NONE`
⇒ **操作系统**判「不可放置」：光标禁止符号、`drop` 永不派发。
**只要用 HTML5 拖放拖 DOM 元素，在这个窗口里就永远放不下**，跟 JS 怎么写无关 ——
V43（`effectAllowed='all'`）、V47、V48（`types` 兜底）、V50（无条件 `preventDefault`）、
V51、V55（放宽校验）六轮补丁全部打在错的层上。**已全删。**

修法：**内部拖拽改指针拖拽**（`mousedown` → 5px 阈值 → 自算落点 + 自绘预览 → `mouseup` 执行）。
配套四件（少一个就出静默故障，见 CONVENTIONS §32.2）：阈值（保双击）、
`mousedown` 当场 `gridSetInteractive(true)`（否则指针滑出命中区后 `mousemove` 断流卡死）、
挂 `window` + `mouseleave` 作废会话、落点复用 `hitDock`/`hitBoxId`（入口优先）。

**同时保住**「从资源管理器拖文件进格子」：真实文件有 `CF_HDROP`，`onDragDropEvent` 照旧。
所以挂件窗的 `drag_drop_enabled` **保持默认 `true`** —— 两条路互斥（官方文档原话：
"Disabling it is required to use HTML5 drag and drop on the frontend on Windows"），
这才是选指针拖拽的真正理由。已在 `grid.rs` 的 Builder 处写死注释，并有断言守着。

### 根因 ②（第 1、3 条）收纳格高度是 `auto`，与引擎几何不一致

`height: isWidget ? box.height : undefined` ⇒ 收纳格高度由内容决定，引擎按
「条目数 ÷ 每行列数」估 —— 不一致就**同时**出两个毛病：盒子长出去**压住下面那个格子**；
盒子自己长高了，内容区与内容等高 ⇒ **没有可滚余量，装不下也不出滚动条**。
第三层隐蔽因素：flex 子项默认 `min-height: auto`，**少了 `min-h-0` 压不下去**。

列表视图最容易撞上：引擎按网格估高（8 条 = 2 行 / 178px），列表是一行一个（8 行 / ≈300px）。

修法：`height: box.height`（**所有**格子）+ 去掉 `maxHeight: isWidget ? …` +
内容区 `flex-1 min-h-0 overflow-y-auto` 三件齐 + 删 `max-h-[60vh]`。

> 旁证：真机库 11 个格子坐标**两两不重叠**（列内间隔一律 24px）⇒ 可见重叠**只可能**
> 来自「渲染高度 ≠ 引擎高度」。

顺带修：`boxViewModes` 从 V51 起是**纯内存** `useState`，切到列表视图**重启就变回网格**
（现在落 `localStorage`）。

## V59.1 — 修「桌面能被滚轮整体上下移动」（用户 09-21 第 4 条反馈）

> 前置：用户确认 V59 的**拖拽与样式已通过**（「现在图标拖动问题解决了，样式也解决了」），
> 随后报出新问题。**这是 V59 自己引入的回归**，不是新需求。

### 用户原话

> 「桌面可以滚轮下上移动了，貌似在另一个电脑有问题 就是整个桌面可以整体通过鼠标滚轮上下移动一点。
> 不过只有鼠标移动到图标或者格子上才可以移动，在桌面空白的地方不能移动」

### 根因

**① 主因：V59 把桌面根画布改成了滚动容器**

```diff
-      className="fixed inset-0 select-none overflow-hidden"
+      className="fixed inset-0 select-none overflow-y-auto grid-scroll"   // ← V59 引入
```

V59 排查「装不下不出滚动条」时顺手改的，还在 `test-drag-pointer.mjs` 白名单里
给它写了理由（「根画布 `fixed inset-0`：整层滚动」）—— **那条理由本身就是 bug**。

机制：根画布 `fixed inset-0`，格子 / 竖条都是它的 `absolute` 子元素；
**绝对定位元素的边框盒超出包含块会撑大包含块的可滚动溢出区** ⇒ 任何一处子元素比视口
高出十几像素，整层就变成可滚容器。再叠加根画布平时 `pointerEvents:'none'`：

| 光标位置 | 命中谁 | 结果 |
|---|---|---|
| 空白处 | 根画布穿透 → explorer | 滚不动（看着「正常」） |
| 图标 / 格子上 | 格子恢复指针事件 → 冒泡到根画布 | **整个桌面跟着滚** |

⇒ 完全对上用户描述的「**只有光标在图标或格子上才可以移动**」。

**② 另一半（「另一个电脑」）：竖条把自己的溢出漏给了根画布**

`loose_strip_rect` 的列数被 `LOOSE_MAX_COLUMNS = 4` 夹住时 `rows = ceil(n/4) > rows_per_col`，
Rust 必须把 `h` 封顶在 `avail_h`，而前端渲染行数仍是 `ceil(n/columns)` ⇒ 内容天然更高。
竖条原本没有 `overflow` ⇒ 多出来的行外溢。**小屏 `avail_h` 更小 ⇒ 更少条目就够触发**，
这是同一处代码在不同分辨率下的**阈值差**，不是两套 bug。

一条反馈里压着**两件不相干的事**：观感（前两句）与功能 bug（后两句）。
先把它们分开，再各自找根因 —— 混在一起查最容易做成「改了样式、双击还是坏的」。

### ★ 双击失效的真根因：穿透态有**两个记账人**

`ignore_cursor_events` 有两条写路：光标轮询线程（每 25ms）与 `grid_set_interactive`
（前端按下 / 抬起条目时）。而 V59 起轮询线程用**局部变量** `last_ignore` 记
「上次我施加了什么」，命令路径直接改窗口**不经过它**：

```
轮询：    set(可交互)    last_ignore = Some(false)
前端抬起：set(穿透)      last_ignore 仍是 Some(false)     ← 记账没跟上
轮询下一拍：算出「该可交互」，!want == false == last_ignore
          ⇒ 判定「不用改」⇒ 跳过 set ⇒ 窗口永久停在穿透态
```

第一次 `mouseup` 后窗口就穿透了 ⇒ 第二次点击落到下层桌面 ⇒ 浏览器**永远凑不齐 `dblclick`**。

**关键指纹**：同一批图标**右键好使、左键不好使**。用户那句「右键打开居然切到资源管理器了」
其实是在替我定位问题 —— `onContextMenu` 不经过 `beginDragSession`，压根没改过窗口状态。
（也说明「右键打开文件夹 = 资源管理器窗口」本身是**正确**的系统行为，不是 bug。）

修法两层：
1. `grid_set_interactive` 按「**强制标志 + 当前光标命中**」求值
   （`let want = interactive || cursor_hit(&win)`）—— 撤掉强制可交互 ≠ 立刻穿透；
2. 穿透态的「上次施加值」提升为**共享原子** `POLLER_IGNORE` + 唯一入口 `apply_ignore`；
   「实际状态不可知」的两条路（窗口创建 / 收起格子）走 `force_ignore`。

### 反馈① 新建便签「一半白一半黑」
- 根因：`NoteWidget` 的便签纸是 `min-h-[90px]`，而承载它的格子卡片高度由引擎按内容算、
  常 >90px —— 纸以下露出卡片深色磨砂底。**不是背景色错，是纸没铺满**。
- 改：`min-h-[90px]` → **`min-h-full`**（90px 保底挪到内层 `RichMarkdown`）。
- 教训：**「一半 X 一半 Y」这种观感，先去查「那个有底色的元素到底铺到哪」**，别急着改配色。

### 反馈② 格子没对齐，要「按分辨率+数量动态算，放不下就滚」
- 旧模型三条一起作祟：① 高度随条目数 ② 两条等宽列 + LPT 分列 ③ `manual` 整块保留历史宽高。
- 新模型 **统一网格 `uniform_grid(count, zone_w, zone_h)`**：所有收纳格同一尺寸（等宽+等高），
  列数在 `1..=4` 里挑 `min(宽,高)` 最大的那一档（`UNIFORM_FLOOR_H=96` / `UNIFORM_MAX_H=480`），
  **行优先自左向右**填；装不下就压到下限并越过下边界，由前端滚动容器接管。
- `manual` 语义变更（推翻 V50「原地不动」第三条）：**只保留位置**（吸附 `nearest_free_cell`），
  尺寸一律统一。
- 前端：收纳格住进 `overflow-y-auto`（宽 = `contentZoneRight`），便签 `position: fixed` 挂出
  滚动层外，`hitBoxId` 把 `scrollTop` 加回，拖拽夹住右沿。
- **V56 那条收尾 clamp 改成只对挂件生效** —— 收纳格越界是「放不下」的正常态，夹回去会叠在同 y。

### 反馈③ 主程序窗口没必要，工具箱弹出框就够

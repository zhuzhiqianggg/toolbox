# 2026-09-24（V75 修正：日历「回到原样式」，只做不改动观感的优化）

## 用户反馈（一句话拍回上一版的激进改法）

> 「就在原来的样式上美化优化，你现在这个跟我桌[面]的主题变差异太大了，还是在现在基础进行优化完善，格子合理的大小」

## 结论：★「借鉴 Win11」只能取**布局 / 空间**层面的改进，不能改**观感**

上一版（V75 第一稿）做了三处**改观感**的改动，全部被否并已回退：

| 上一版改动 | 处置 |
|---|---|
| 日期数字包进**圆形高亮**（选中实心圆 / 今天描边圆） | ❌ 回退 → 恢复**整块高亮**（`theme.selected` / `theme.today` 套在格子上） |
| 表头加大到 15px、`干支`压成「丙午·马」、导航归组 | ❌ 回退 → 恢复 13px「2026 年 9 月」+「丙午年 · 属马」药丸 + 原导航 |
| 格子内 `py-1 gap-0.5`、休/班挪 `right-0.5 top-0.5`、标记行 8px | ❌ 回退 → 恢复 `py-0.5` / `right-0 top-0` / 标记行 9px |

**保留的唯一改动**：`buildMonthGrid(year, month, fit=true)` **自适应行数**（5 或 6 行）。
它只删掉「月末那一整行全是下月日期」的空白（约 54px），**不改任何配色 / 字号 / 高亮形态** ——
正好对上用户说的「格子合理的大小」：同样的正方格（≈54px，V48 用户明确要的），整体比例更紧凑、不浪费。

⇒ 判据：**用户说「参考某产品」时，先分清他要的是「布局/信息密度」还是「视觉风格」**；
本项目桌面层是玻璃质感 + 深色玻璃日历主题，硬套 Win11 实心圆会跟桌面脱节。

# 2026-09-24 深夜 V76：日历「高度」与「上下不清晰」的根因（已定位 + 部分修好）

## 用户反馈

> 「这个高度合理吗？ 而且上下每个日 貌似看着也不清晰」（附截图：工作台日历，主题选择器展开）

## ★ 关键教训：别靠肉眼估截图，写脚本量

`.build-logs/measure-calendar.py` + `measure-calendar2.py`（PIL；**venv 里没有 numpy**，纯 Python 循环够用）。
换算基准：色板 `bg-amber-300` 圆点 = `h-4 w-4` = 16 CSS px = 24 设备像素 ⇒ **用户显示比例 1.5**。
实测结果：

| 项 | 实测 | 结论 |
|---|---|---|
| 选中格（`bg-sky-500` 实心块）包围盒 | 78×78 设备px = **52×52 CSS px** | ★ 格子**本来就是正方**、行距 53 ⇒「高度不合理」不是格子被拉长 |
| 格子内容 | 数字 dy 2-15、农历 17-27、标记 31-40（共 ~40px / 53px 格） | 内容只占上半格，底部约 13px 空档 |
| 琥珀点（`bg-amber-500`）中心 | 离**自己**那天的数字 **35.5px**；离**下一天**的数字 **17.5px** | ★ 根因：`mt-auto` 把点压到格底 ⇒ **点离下一天的数字更近一半** |

⇒ 「上下每个日 看着也不清晰」= **标记归属看着像下面那天**（不是上/下月的日期太淡 —— 那是另一半，见下）。
⇒ 用户手画的红框量出来是全格高、但只有 35-42px 宽（比格窄）⇒ 他圈的是「数字+农历+点」那一列，不是格边界。

## 已改（`src/modules/desktop-grid/DesktopWidgets.tsx`，只有两处）

1. 标记行 `mt-auto` → `mt-1`：标记紧跟自己那天的农历（相隔 4px），不再被压到格子底部。
   数字行**仍然全部对齐**（标记行恒占 `h-[9px]`，不随有无计划变化）。
2. 上/下个月日期 `opacity-35` → `opacity-50`：原来「31 号」和「1-4 号」淡到读不出数字。

`tsc --noEmit` 0。**尚未打包装机**（等高度拍板，避免装两次）。

## 待用户拍板：格子高度（这是「这个高度合理吗」的正面回答）

格宽固定 ≈ 53px（工作台 400px / 7 列），内容需要 **~42px**
（数字 13 + 2 + 农历 10 + 4 + 标记 9 + 上下 `py-0.5` 4）。于是：

- **正方 53×53**（V48 用户明确要的「每个字正方形」）⇒ 每格底部留 13px 空档，这正是「高度不合理」的来源；
- **紧凑 53×44**（`aspect-[6/5]`）⇒ 日历整体矮 **48px**；代价是格子略宽于高。

两版都已在浏览器实测（53×53 / 53×44，内容 40px 不裁切）。对比图 `.build-logs/compare-v76.png`（①修复前 ②正方 ③紧凑）。

## ★ 新增可复用手段：浏览器预览页跑「真机数据」

浏览器里 `@/lib/ipc` 的 `call()` 先判 `isTauri()`（= `'__TAURI_INTERNALS__' in window`），
所以只要在页面里塞一个 `window.__TAURI_INTERNALS__ = { invoke(cmd){…} }`，**真实组件就能拿到真机数据**（本次是 `handy.db` 的 64 条 `todos`）。

- 生成器 `.build-logs/make-mock-tauri.py`；探针 `.build-logs/probe-dots.js`（顺带量格子几何）。
- ⚠️ **`agent-browser open --init-script <path>` 实测不生效**（正斜杠/反斜杠路径都试过，`window.__HANDY_MOCK__` 始终 false）。
  可行做法：**临时包装页** —— 复制 `index.html`、在 `<script type="module">` 之前插入桩，
  再 `open http://127.0.0.1:5199/mock-calendar.html?demo=calendar`。**用完立刻删**（别留在仓库根目录）。
- 用 `agent-browser eval` 注入 `<style>` 就能**不改代码比较候选方案**（本次的正方/紧凑就是这么比的）。
- 环境坑：`agent-browser open` 冷启动极慢（首次卡了 5 分钟才返回），之后 `eval`/`screenshot` 秒回 ⇒ 冷启动那次给足超时。
